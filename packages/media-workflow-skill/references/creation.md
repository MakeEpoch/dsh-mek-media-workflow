# 制作指导

## 把需求变成表达方案

先从用户已有信息判断：给谁看、看完应知道或能做什么、必须保留什么、希望是什么观看感受。视频任务把核心目标、信息主次、限制与时长写入 brief 的 description/requirements，将表达、视觉、语气和参考写入 creative；文章与贴图按 [formats.md](formats.md) 组织相应制作方案。只有会改变方向的缺口才需要问；不要让用户为每个字号、转场或镜头选项填表。

内容类型与画面风格分别决定。资讯可以是简洁说明、深度解释或现场报道；产品内容可以是上手教程、功能演示、场景说明或发布片。用户没有要求高强度营销时，不自动添加夸张钩子、密集音效或口号。用户要求正式、克制或保留完整流程时，按其目的取舍。

例如“让新用户学会导出报表”应围绕实际操作和结果组织；“介绍这次更新为什么有用”应围绕变化、使用场景和证据组织。两者即使用同一份资料，也不应该得到同一套文案和分镜。

## 选择能兑现方案的制作路径

| 路径 | 适合 | 当前边界 |
| --- | --- | --- |
| 当前对话 + 任务 CLI | 需要讨论角度、查看截图、查资料、迭代内容的任务 | 助手要实际消费生成请求和回读状态；工作台不会自动把 JSON 请求发到聊天 |
| 工作台模型 + 内置 FFmpeg | 单张素材配标题、同步字幕的基础视频 | 固定版式、每段一个镜头、每镜头只使用一份视觉素材 |
| 工作台模型 + 内置 huashu | 需要可编辑模板工程的基础动态视频 | 仍为固定布局；仅有限平移/缩放；整段文稿按场景显示，不直接使用词级字幕切分 |
| 当前对话 + 专业制作工具的定制工程 | 用户要求特定布局、信息卡、多素材、图表、演示焦点或复杂动效 | 按环境中实际可用技能/工具制作，完成预览与质检后按交付导入协议回纳实际文件和工程 |

先判断用户要求能否被实际执行器表达。visual/treatment 的说明不会变成代码，切换到 huashu 后端也不会自动成为定制导演制作。内置模板不能实现的明确要求，用 unresolved 指出需要的能力或工程，不在描述里承诺后继续产出基础模板。

采用定制制作时仍沿用同一资料根与任务 ID，保留工程和交付路径。准确区分“插件已记录的阶段”和“任务外已完成的定制产物”。完成本任务的预览和质检后，使用 [交付导入](imports.md) 将实际文件保存为正式交付新版本；未导入前说明任务外路径，不直接修改 manifest/state/审批，也不另建同名任务。超出当前文件体积、依赖或工具能力的部分单独说明。

## 来源与素材要被实际理解

原文阅读要保留上下文、时间、对象和数字单位；事实表只提取与本次角度有关的证据。检查 claim 是否被 quote 支持，而不仅是 quote 能否在原文里搜到。用户的制作限制、未知事项和音乐说明不应混入报道事实。

截图、录屏、Logo 和配图要实际查看：内容是什么、哪块能支持讲解、手机上能否读清、能否裁切、哪些示例数据不应被引用。素材文件存在和 MIME 正确不能代替视觉理解。工作台自动模型目前只收到元数据；没有查看能力时保留待检查，不能声称已确认画面重点。

缺少真实界面时不编造 UI。根据用户目的，使用有证据的文字或示意表达是否可行，应在方案中明确；当前 product 流程要求真实截图/录屏、Logo 与品牌出处，不要通过换成 news 绕过素材检查。

## 写脚本与安排镜头

让每段承担一个信息任务：建立关注、解释要点、给出证据、演示操作或收束。结构随内容变化，不强制每片都有这些段落，也不默认照搬原文章节或“第一、第二、第三”。标题写观众要知道的内容，避免用“开场”“功能展示”等内部制作标签充当成片文案。

口播使用能自然读出的短句，处理外文名、数字、日期和单位；屏幕文案可以更短，突出观众此刻需要看的信息。当前内置 schema 的 section.text 同时用于口播和字幕，不能凭空增加一个执行器不读取的屏幕文案字段。

分镜明确画面承载什么、使用哪份真实素材、怎样配合旁白。内置模板必须保持脚本段落与镜头顺序一致、每段一个镜头。需要同段内多镜头或独立画面节奏时使用定制工程，不把丰富设计藏在 visual 字符串里。

时长先估算、再以实际配音核对。有旁白时，内置镜头跟随音频段，修改 durationSeconds 不会自动加速旁白或增加切镜。超出用户约定时长时调整实际文稿与镜头，不随意提高语速；有明确内容范围时也不能为了短片节奏静默删掉关键要求。

## 检查实际作品并落实修改

制作中自行检查、修正，不新增用户没有选择的评审关。按需要查看开场、转场、信息密集处和收尾，并正常速度播放；工具不能播放或听审时准确说明范围。

- 对照需求：重点、范围、时长和视觉方向有没有兑现？
- 对照事实：数字、单位、时间和适用条件是否一致，建议有没有混成事实？
- 对照画面：目标屏幕上能否读清，截图是否支持正在讲的内容，是否遮挡关键操作？
- 对照音频：配音是否自然，字幕是否跟得上，音乐是否盖住人声，切换是否打断理解？

不要把技术全绿当成内容验收。QA 的 unknown 应具体到尚未判断的项目，并说明所需证据；无法查看时不凭空判 pass，也不因偏好性判断一律增加阻塞。

收到反馈后先定位负责的输入：事实/表达回到资料或脚本，节奏回到脚本/分镜/音频，布局与视觉效果回到工程，字号与边距可在内置合成/成片参数中调整。按照实际改动记录说明，保留旧版，不能仅改字号就声称修好了布局。内置修改不支持时集中说明上游调整路径，遵守现有 requirements/review/redo 协议，保持本次评审策略。

## 交付说明

给出成片、可编辑工程、封面或字幕等实际交付路径，说明素材出处、任务 ID、已做的检查和未覆盖的判断。封面应符合平台用途；内置 cover.png 只是首帧抽取，没有自动完成独立封面设计。分镜文档、流程 complete 与文件可解码都不能取代对作品的实际判断。
